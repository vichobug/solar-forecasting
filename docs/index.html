Field primer

Reading a magnetogram for trouble

Three things worth knowing before the log below makes sense.

01

The signal

Each sample is a 12-hour lookback window (60 timesteps at 12-minute cadence) of 24 SHARP magnetic-field parameters — drawn from 4,000+ active regions across 9 years of SDO observations (2010–2018).

02

The imbalance

Large flares are rare — about 2% of real observations. Train partitions are synthetically rebalanced toward 50/50; test is left natural. That gap is most of this story.

03

The scorecard

Accuracy is meaningless at 2% prevalence. TSS (recall minus false-alarm rate) and HSS (skill over chance) are the field-standard metrics used throughout.

Mission log

Eight entries, in order

The chronological record — including the two bugs that mattered more than any architecture choice.

01baseline

Baseline established

Loaded ~98k training / 331k test sequences. A naive Logistic Regression and HistGradientBoosting model, trained on hand-aggregated summary stats (mean / std / min / max / last per parameter), got the project off the ground.

02deep learning

Raw sequences, real networks

Built a 1D-CNN and an LSTM in PyTorch to learn directly from the raw (60, 24) time series instead of hand-aggregated stats — full control over an imbalance-aware loss.

03incident

The machine went down

First training run exhausted memory and hard-rebooted an 8GB M1. Loading five test partitions as float64, then casting to float32, spiked memory ~5.4GB with both copies alive at once. Fixed with a streaming loader, a memory guard, and an active watchdog process.

04bug

A validation score that lied

CNN validation TSS hit 0.90 — above even the published ceiling. Cause: validating on a held-out train partition let TimeGAN-synthesized near-duplicate sequences leak across folds.

val TSS 0.90 → real test TSS 0.48
05fix

Honest validation, honest number

Rebuilt validation on an untouched, natural-distribution test partition instead. The score dropped to a defensible 0.51 — but training now visibly collapsed to predicting one class for stretches of several epochs.

06bug

The real mismatch

Train partitions are resampled to ~1:1; test is naturally ~52:1. A class weight applied to the already-balanced training data was a no-op. Undersampling positives to a ~10:1 ratio and applying a matching weight fixed the calibration.

CNN test TSS 0.51 → 0.66
07ensemble

A tree search, and a segfault

Paired the CNN with a freshly-tuned gradient-boosted ensemble. The 40-iteration search crashed three times with SIGSEGV — the tree library's internal thread pool colliding with joblib's own parallelism on constrained hardware. Capping the thread count fixed it.

08result

The tree wins

The tuned gradient-boosted model alone reached 0.84 — past the CONTREX benchmark, using hand-aggregated features and a proper search, no raw sequence modeling required. Verified stable across all five held-out test partitions (0.82–0.87 individually).

Field notes

Two problems that had nothing to do with modeling

Hardware

Memory spike, hard reboot

An 8GB machine can't hold a float64 copy and a float32 copy of a multi-gigabyte test set at once. The fix was structural, not clever: stream one partition at a time, check available memory before every heavy step, and run an active watchdog that kills the process before the OS has to.

Runtime

A segfault inside the tree library

HistGradientBoostingClassifier's internal OpenMP binning step crashed under joblib's process-level parallelism on this machine — three times, always mid-search. OMP_NUM_THREADS=1 combined with a modest n_jobs resolved it without giving up real parallelism.
